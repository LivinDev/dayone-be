## Real data loss in production from this migration — 2026-09-17 (follow-up)

The three-step migration below (additive → backfill → destructive) was designed and verified carefully — **but only against local dev's database.** The backfill script (step 2) was only ever run locally; nobody checked whether **production** had its own separate real Story data that also needed backfilling before the destructive step (step 3, dropping `TimelineEntry.images`/`caption`) ran there too. It did have real data — the founder had added images to a Story in production before this deploy — and confirmed those images' database records are now gone (test data, not a real end-customer's, so accepted as an acceptable loss rather than chased for recovery). The image *files* themselves are very likely still sitting in S3 untouched — migrations only touch the database — but nothing can find them without their exact URLs, and this project's S3 IAM user has no `ListBucket` permission to browse for them.

**How to apply — this is the real lesson, not the specific incident**: any future migration that drops a column/table with a backfill step must ask **"does production also have real data that needs this same treatment?"** before the destructive step runs anywhere, not just verify against whichever database happened to be open during development. Local dev and production are separate databases sharing only a schema, not rows (see the root `CLAUDE.md`'s matching note) — protecting one's data says nothing about the other's. Going forward: before any destructive migration touches production, either confirm production has no data in the affected columns, or run the equivalent backfill against production specifically (not just locally) before the drop step ships.

## Per-image captions + multi-section days — 2026-09-17

Founder-requested restructuring, planned before building (per their own "make a plan first" instruction) since it touched the schema and needed a real data migration, not just new fields. Two structural changes: (1) each image now carries its own caption, not the whole entry; (2) a day can hold multiple sections — small captioned groups of images — instead of one flat gallery. Two levels deeper than the original `TimelineEntry.images: String[]`/`caption`.

**New shape**: `TimelineEntry` (a "day" — `location`/`occasion`/`entryDate` stay here) → `TimelineSection[]` (a moment within the day, own optional `caption`, `order`) → `TimelineImage[]` (own `url`, `caption`, `order`).

**Migration, done in three deliberate steps, not one** — the founder's real entry (their real birthday photos, real caption, real location) was live in the old flat shape and could not be lost:
1. **Additive migration** (`20260917010000_add_timeline_sections_images`) — created `TimelineSection`/`TimelineImage`, left `TimelineEntry.images`/`caption` untouched. Zero risk, nothing reads the new tables yet.
2. **One-off backfill script** (`prisma/backfill-timeline-sections.ts`, run once via `ts-node`, then deleted — not committed) — wrapped every existing entry's `images`+`caption` into one auto-created section (`order: 0`, section `caption` = the old entry `caption`, one `TimelineImage` per old url). Verified the founder's real 2-image entry round-tripped byte-for-byte (same URLs, same order, same caption text) via direct SQL before proceeding.
3. **Destructive migration** (`20260917010500_drop_timeline_entry_flat_fields`) — only run after step 2 was confirmed correct — drops `TimelineEntry.images`/`caption`.

**API shape** — sections' images are submitted as a full replaceable array on save (same "resubmit the whole list" convention `Product.images` already uses), not fine-grained per-image endpoints:
- `POST /nfc-tags/:tagId/timeline` — creates a day **and** its first section(s) in one nested Prisma write: `{ location?, occasion?, entryDate?, sections: [{ caption?, images: [{url, caption?}] }] }`.
- `PATCH /timeline/:id` — day-level fields only now (`location`/`occasion`/`entryDate`) — sections/images moved to their own endpoints below.
- `POST /timeline/:entryId/sections` — add a section to an existing day.
- `PATCH /timeline/sections/:id` — replace a section's caption + full images array.
- `DELETE /timeline/sections/:id` — remove one section (explicit ordered delete of its images first — no `onDelete: Cascade`, same standing convention as Addresses).
- `DELETE /timeline/:id` (whole day) now also explicitly cascades through sections→images itself, for the same reason.

New DTOs: `ImageInputDto` (`url`, optional `caption`), `SectionInputDto` (optional `caption`, `images: ImageInputDto[]`, 1–6 each — nested-validated via `class-validator`'s `@ValidateNested`/`class-transformer`'s `@Type`), `UpdateSectionDto` (same shape, all optional).

Verified live: migration steps re-confirmed via direct SQL after each one (founder's entry intact throughout — 2 images, correct order, correct caption, correct location/occasion — never touched); new nested create/read/update/delete routes curl-tested; then the full real UI flow via Playwright (see `dayone-web/CLAUDE.md`'s matching note) — a 2-section day with per-image captions, composed, previewed, saved, and rendered correctly on the real public Story page, plus the founder's actual real entry loading correctly through the new nested API and rendering on their live page with zero regressions.

**How to apply**: Any future editor for this data must resubmit a section's *entire* image list on change (add/remove/reorder are all "here's the new full array"), not attempt per-image add/remove calls — that's the one thing this API deliberately doesn't support, to keep the surface small.

## NFC Story feature — the V2 timeline, built for real — 2026-09-16

Founder asked for a second option alongside the existing plain Link destination: a "Story" — a colorful, owner-built timeline of dated moments (photos, a location, a caption) tied to a claimed garment. This is literally the `TimelineEntry`/`EntryStatus` model that's sat scaffolded-but-explicitly-unbuilt since the very first migration ("V2 ONLY — do not build until instructed" in the schema comment) — now built, on the founder's explicit go-ahead, with two real scope decisions confirmed with them first, not assumed:

1. **Repeating timeline** (many dated entries over time), not a single one-off page — the bigger of the two options discussed, matching the original V2 concept rather than a smaller "one story per tag" alternative.
2. **Publishes instantly, no moderation queue** — a real divergence from the schema's own `PENDING`-by-default design, which existed specifically because moderating user-uploaded photo content was flagged as an India IT Act consideration, not a style choice (see `TimelineEntry`'s original comment). Flagged to the founder before building; they chose instant-publish anyway. **Not silently dropped, hedged cheaply instead**: `EntryStatus` still exists and every entry still gets a status (now defaulting to `APPROVED` instead of `PENDING`), and `findPublicForTag`/`findMineForTag` still filter on it — turning moderation on later is a default-value + admin-queue-UI change, not a schema migration.

**Schema** (migration `20260916223000_nfc_story_feature`): `NfcTag` gained `destinationKind` (`LINK | STORY`, nullable — null means the owner claimed but hasn't picked yet) and `storyTheme` (`SUNSET_BLOOM | OCEAN_TIDE | FOREST_MOSS | MONO_ARCHIVE`, only meaningful once `destinationKind = STORY`). `TimelineEntry.photoUrl` (singular) became `images String[]` (matches `Product.images`'s existing array-column convention, not a new join table) and gained `location String?`. `entryDate` and `status` both got real defaults (`now()`, `APPROVED`) so a create doesn't need every field typed out.

**Why `destinationKind` lives on `NfcTag`, not `Destination`**: a Story has no single URL to store — its content *is* the timeline entries. Only `LINK` mode ever creates/upserts a `Destination` row; `STORY` mode leaves it untouched and unused.

**New `src/timeline/` module** (`TimelineController`/`TimelineService`): `POST /nfc-tags/:tagId/timeline` (owner-only, create), `PATCH`/`DELETE /timeline/:id` (owner-only, same 404-not-403 ownership pattern as Addresses/Reviews/NfcTag destinations), `GET /nfc-tags/:tagId/timeline` (**public** — anyone tapping the tag or visiting the eventual `/story/:code` page reads this, no auth, same reasoning as `Destination.url` already being public), `GET /nfc-tags/:tagId/timeline/mine` (owner-only, sees everything including not-yet-approved — a no-op today, real once moderation exists). `POST /timeline/uploads` reuses the exact lazy-`S3Client` pattern from `ProductsService`/`InvoicesService` verbatim, just a new `timeline/` key prefix — any authenticated role can upload to their own story, not Admin/Manager-gated like Products' uploader.

**`NfcTagsService` extended**: new `PATCH /nfc-tags/:id/destination-kind` (owner-only) sets `destinationKind` and, for `STORY`, `storyTheme` (defaults to `SUNSET_BLOOM` if omitted — changeable anytime, not a one-shot choice, matching this codebase's general "trust internal actors, don't over-engineer a state machine" stance already used for Order status transitions). `getClaimInfo` now returns three distinct resume states instead of one (`needsDestinationChoice` / `needsDestination` / `destinationKind`+`storyTheme`) so the claim page always knows exactly which step to land an owner on. `GET /t/:code` (`TapRedirectController`) gained a `STORY` branch — redirects to `${FRONTEND_ORIGIN}/story/:code` instead of `Destination.url`; `LINK` and unclaimed/undecided behavior is unchanged.

Verified live end-to-end with curl (throwaway data): generate → assign → claim → `needsDestinationChoice: true` → choose Story + a theme → `destinationKind`/`storyTheme` persist and read back correctly → create an entry → public (unauthenticated) read returns it → `GET /t/:code` 302s to `/story/:code`. - **`src/common/utils/gst-state-codes.ts`** — the fixed 38-entry GST state/UT code table (govt-published, verified via search), used to render "place of supply" the conventional way (`Karnataka (29)`, `Delhi (07)`) for both seller and buyer. ## NFC tag system (build order step 6 — backend done, verified end-to-end, 2026-09-08)

The actual core V1 mechanic (tap the shirt → your link) — `src/nfc-tags/` (`NfcTagsController` + `TapRedirectController`, sharing one `NfcTagsService`). No schema change needed, `NfcTag`/`Destination`/`TagStatus` already existed in `prisma/schema.prisma`, unused until now.

**The flow, precisely**: a tag's lifecycle has three separate steps, each owned by a different actor —
1. **Generate** (`POST /nfc-tags/admin/bulk-generate`, Admin/Manager) — mints N `UNCLAIMED` tags with unique 8-char codes, ahead of manufacturing. This has to happen before the physical chips get written, not after.
2. **Assign** (`PATCH /nfc-tags/admin/:id/assign`, Admin/Manager) — at fulfillment/packing time, links one specific tag to one specific sold `OrderItem` (`UNCLAIMED → ASSIGNED`). Deliberately *not* automatic at checkout — staff don't know which physical shirt off the shelf will get packed until they're packing it.
3. **Claim** (`POST /nfc-tags/claim`, public) — the buyer proves ownership with Order ID + the email their order was placed under (`ASSIGNED → CLAIMED`, `ownerId` set to the order's actual buyer — never taken from the request body itself, the email match is what verifies identity).

**Tag ↔ shirt is per physical unit, not per variant or per product** — `NfcTag.orderItemId` is a nullable `@unique` FK to `OrderItem`, so two customers buying the identical color+size variant still get two completely independent tags. This already fell naturally out of the existing "no quantity field, one `OrderItem` row per physical shirt" schema decision from the Product Variants phase — nothing new needed there.

**`GET /t/:code`** — the tap-redirect, its own controller (`TapRedirectController`, `@Controller('t')`) at the app root, not nested under `/nfc-tags`, so the permanent physical-tag URL stays short (`day01.store/t/A7K2XQ`). No global route prefix exists in `main.ts`, so this sits cleanly at root with no collision. `ASSIGNED`/`UNCLAIMED` → 302 to `${FRONTEND_ORIGIN}/claim/:code`; `CLAIMED` → 302 straight to `Destination.url`.

**Two real gaps flagged during planning and closed before building, not left as known issues:**
- **Unknown/broken codes degrade gracefully, not a bare 404** — a customer standing there with a shirt shouldn't hit a dead-looking error page over a manufacturing typo or an orphaned code. `GET /t/:code` 302s to the frontend homepage (`FRONTEND_ORIGIN`) for any code it can't resolve — including the edge case of a `CLAIMED` tag with no `Destination` row somehow (shouldn't happen, the claim flow prompts for one immediately, but falls back safely rather than sending an already-owned tag back through the claim form where it'd just get rejected as "already claimed").
- **`POST /nfc-tags/claim` is rate-limited** — `@nestjs/throttler` newly added, 5 requests/minute per IP, applied via `@UseGuards(ThrottlerGuard)` on *only* this one route (not registered as a global `APP_GUARD`, so nothing else in the app is throttled). This is the one public endpoint that grants ownership from just an Order ID + email — without a limit, someone who knows (or guesses) a tag's code could script Order-ID/email guesses against it. Verified live: the 6th claim attempt inside a minute from the same IP correctly 429s.

**Other rules enforced in `NfcTagsService`**: codes are 8 chars over a 32-letter alphabet that excludes visually-ambiguous characters (`0/O`, `1/I/L` — these get physically printed/engraved next to the chip); assign only succeeds from `UNCLAIMED` and only onto an `OrderItem` that doesn't already have a tag; claim only succeeds from `ASSIGNED` (can't claim an unlinked tag, can't re-claim a claimed one); `PATCH /nfc-tags/:id/destination` (the owner editing their link afterward) 404s — not 403s — on a tag that isn't theirs, same "don't confirm existence" pattern as Addresses/Reviews; `GET /nfc-tags/by-code/:code` (used by the claim page) returns `{code, status, destinationUrl}` — `destinationUrl` only populated once `CLAIMED`, no other PII (never the linked order/owner). Returning the link here isn't a new leak: anyone tapping the physical tag already lands on that same URL via `GET /t/:code`. **Update 2026-09-08**: this endpoint's shape changed the same day to add `destinationUrl` — see `dayone-web/CLAUDE.md`'s "NFC claim landing page" note, which also simplified `GET /t/:code`'s own fallback (a claimed-but-no-destination tag now routes to `/claim/:code` like any other not-yet-fully-set-up tag, instead of a separate homepage fallback).

**Third update, same day — real bug fix.** `getClaimInfo` originally only recognized "eligible to claim" (`status === ASSIGNED`); once a tag flipped to `CLAIMED`, a caller returning to the claim page without ever setting a destination got a false "not linked to any of your orders" message — hit for real on the founder's own tag. Fixed by adding `ownedByMe`/`needsDestination` to the response (see `dayone-web/CLAUDE.md`'s matching note) — a `CLAIMED` tag with no `Destination` and `ownerId === userId` now correctly routes back to the add-a-link step instead.

**Fourth update, same day — Account Home's "NFC & Garments" tab built** (`dayone-web`'s `garments-tab.tsx`), consuming `GET /nfc-tags/my` and `PATCH /nfc-tags/:id/destination` — both already existed, no backend change needed. This closes out the NFC system's frontend entirely; see `dayone-web/CLAUDE.md`'s matching note.

**Known operational gaps, surfaced 2026-09-08 but not built** — none of these block a first deploy, flagged for whenever real day-to-day tag operations start mattering:
- No **unassign** — if staff link the wrong tag to an order item while packing, there's no way to reverse it (`PATCH .../assign` only works from `UNCLAIMED`, and there's no endpoint to go back).
- No way to **retire/void** a damaged, lost, or mis-printed tag — it just sits `UNCLAIMED` forever with no "dead" state.
- No **CSV export** of freshly generated codes — the admin UI shows them in a copy-paste textarea only, fine for a handful, not for a large batch.
- No **audit trail** — current state is tracked, but not who assigned what or when.

## Production deploy — CORS fix + a real `FRONTEND_ORIGIN` bug found and fixed — 2026-09-09

Founder deployed this backend to `https://api.day01.store` (EC2, pm2, nginx reverse-proxying 443→4000) sometime after the 2026-09-08 session ended — discovered indirectly this session (`dayone-web/.env.local` was already pointing at the live URL). Two real issues surfaced once the deployed backend was actually exercised:

**1. CORS only ever allowed one origin.** `main.ts` had `app.enableCors({ origin: process.env.FRONTEND_ORIGIN })` — a single string. Once `FRONTEND_ORIGIN` on the server was set to the real `https://day01.store`, a local frontend dev server (`localhost:3000`) calling the live API for testing got blocked. Fixed by adding an optional, additive `CORS_EXTRA_ORIGINS` (comma-separated) env var — `FRONTEND_ORIGIN` stays the one canonical value (also what the tap/claim redirects use, see below), `CORS_EXTRA_ORIGINS` is purely extra allowed callers. Verified with curl against a throwaway local instance: both origins get `Access-Control-Allow-Origin` echoed back, an arbitrary third origin doesn't.

**2. Real bug, not a config/restart issue — `GET /t/:code` and `/claim/:code` fallbacks were permanently stuck on `localhost:3000` in production, no matter what `.env` said or how many times the process was restarted.** Root cause: `tap-redirect.controller.ts` read `FRONTEND_ORIGIN` into a **module-level constant** (`const FRONTEND_ORIGIN = process.env.FRONTEND_ORIGIN ?? 'http://localhost:3000'`). TypeScript compiles this file's imports (reached transitively via `main.ts`'s `import { AppModule } from './app.module'`) into `require()` calls that get hoisted **above** any other top-level code in the compiled output — including `main.ts`'s own `process.loadEnvFile('.env')` call, even though that line is written *after* the imports in the source. So this constant was evaluated with `process.env.FRONTEND_ORIGIN` still `undefined`, on every single boot, deterministically — the `.env` file being correct never mattered, and no amount of `pm2 restart`/`--update-env` could ever have fixed it, since the bug reproduces identically on every fresh process start. **This is the exact same bug class already hit once before in this codebase** (`JwtModule.register()` reading `JWT_SECRET` at module-decoration time — see the "Auth + role system" section below) — that one got the `registerAsync()` fix; this one didn't get the equivalent treatment when it was written.

Diagnosed by first ruling out the obvious suspects (confirmed the deployed `.env` was already correct via `cat`; confirmed pm2 wasn't caching a stale value via `pm2 env 0`; confirmed `main.ts`'s own CORS line *was* correctly reading the env var, visible directly in the response's `Access-Control-Allow-Origin` header) — which narrowed it down to a per-file problem, then found the module-level `const` was the one place still doing an eager read. **Fixed by moving the read inside `tap()`'s method body** (`const frontendOrigin = process.env.FRONTEND_ORIGIN ?? 'http://localhost:3000';`, evaluated fresh per-request, long after `loadEnvFile` has already run) — matches the "defer the read" pattern already established for the Jwt bug. Verified locally: a throwaway instance started with `FRONTEND_ORIGIN=https://day01.store` now correctly 302s an unknown code straight to `https://day01.store` instead of falling back to localhost.

**This fix applies retroactively to every existing tag, not just newly generated ones** — nothing about this URL is stored per-tag in the database; it's computed fresh on every request from the env var. The moment the fixed code is deployed, the very next tap on any of the founder's 3 real tags (`5FQPBX2H`, `9FK3QD5W`, `PPEBDWQ8`) redirects correctly — no backfill or regeneration needed. `Destination.url` (the actual link an owner sets after claiming) is separate, stored per-tag, and was never affected by this bug either way.

**Deployed 2026-09-09, later the same day** — the founder redeployed `dayone-be` to EC2 (`git pull && pnpm run build && pm2 restart dayone-be --update-env`, same session that also shipped Categories + MRP below), so both fixes are now live. Confirmed indirectly: `GET /categories` and `GET /products` against `api.day01.store` return the new schema, which only exists in a build that includes every commit up through this point — so this fix necessarily shipped in the same deploy. Not separately re-verified with a live tap on one of the founder's real tags after this specific deploy, but there's no reason to expect it didn't take effect along with everything else.

**Real secrets exposure, flagged to the founder**: while debugging, the founder pasted the live `.env` contents (DB password, `JWT_SECRET`, AWS access key + secret, and a GitHub PAT) directly into chat. Flagged immediately — recommended rotating all four (AWS key/secret via IAM, GitHub token via revoke+reissue, `JWT_SECRET` via a fresh random value, DB password lower-priority since it's only reachable inside the server). Not confirmed whether the founder has rotated them yet as of this session — worth checking next time this comes up, don't assume it's been done.

**How to apply:** Any other `const X = process.env.Y ?? fallback` written at module scope anywhere in this codebase has the same latent bug — a fresh `grep -rn "process\.env\." src` audit (done this session, only this one file had it outside the already-fixed `JwtModule`/lazily-constructed `S3Client`/constructor-time reads) is worth repeating if a new module gets added that touches `process.env`. The safe patterns already established in this codebase: read inside a method body (this fix, `ProductsService.uploadImage`'s lazy `S3Client`), inside a constructor (`JwtStrategy`, `PrismaService` — constructors run at DI-instantiation time, after bootstrap starts), or via `registerAsync`'s `useFactory` (`AuthModule`'s `JwtModule`) — never a bare top-level `const`.

## MRP vs Selling Price / discount % — 2026-09-09 (same day, follow-up)

Founder-requested gap, surfaced during a research pass comparing this admin against Shopify/Indian D2C conventions: there was only ever one price field anywhere, so no "was ₹X" discount could be shown. Fixed by adding an optional `mrpInPaise` alongside every existing `priceInPaise`, mirroring the exact override pattern already used for price.

- **Schema**: `Product.mrpInPaise Int?` and `ProductVariant.mrpInPaise Int?` (variant-level optional override, falls back to `Product.mrpInPaise` if null — identical fallback semantics to the existing `priceInPaise` override). Migration `20260909140000_mrp_pricing`, purely additive/nullable, non-breaking.
- **Discount % is never stored** — computed live from `mrp`/`price` on the frontend only (`discountPercent()` in `dayone-web/src/lib/utils.ts`), matching the Indian e-commerce convention (Myntra/Ajio/Amazon.in) of two separate price fields with the discount derived on render, not a persisted third column.
- **Validated server-side**: `ProductsService`/`VariantsService` both reject (400) an MRP set below the effective selling price — a "was" price lower than the actual price isn't a discount, it's just wrong data. On `Product`, this is a plain same-request comparison; on `ProductVariant` it resolves the *effective* selling price first (`dto.priceInPaise ?? existing.priceInPaise ?? product.priceInPaise`, fetching the parent product only when neither the request nor the existing variant already has a price to compare against).
- DTOs (`create-product.dto.ts`/`update-product.dto.ts`/`create-variant.dto.ts`/`update-variant.dto.ts`) all gained `mrpInPaise?: number` (`@IsInt() @Min(1)`), same style as every other optional money field in this codebase.

Verified live with curl: setting a valid product-level MRP persists; setting one below price 400s; the same two checks repeated at the variant-override level (including the case where the variant has its own price override to validate against). Then verified through the real admin UI (see `dayone-web/CLAUDE.md`'s matching note) — the discount actually renders correctly on the storefront end to end.

**How to apply:** Any future money field on `Product`/`ProductVariant` should follow this exact shape — nullable at both levels with variant falling back to product, never stored derived data (discount %, in this case) that could drift out of sync with its inputs.

**The one real production wrinkle handled carefully**: `day01_db` had exactly one real order already (the founder's own, via `john@dayone.com`, placed while testing Checkout earlier). Made `OrderItem.variantId` **nullable** specifically so that row didn't need a fabricated variant invented to satisfy a NOT NULL constraint — verified post-migration that its `variantId`/`color` came back `null` and everything else was untouched.

**Dual order-creation path in `OrdersService.create`** — this is the part worth understanding before touching this code again: `CreateOrderDto` items accept *either* `{ variantId, quantity }` (real stock tracking) *or* the legacy `{ productId, size, quantity }` shape. The legacy path exists **only** so the 14 existing products (all variant-less at the time) didn't become unorderable the moment this shipped — real stock decrement only happens on the variant path (atomic `updateMany` guarded by `stockQuantity: { gte: needed }`, checked via affected-row count, so two concurrent checkouts can't both succeed past the last unit). The legacy path has **no stock check at all** (same as before variants existed) and is **rejected with a clear message the moment a product actually gets a real variant** — `product.variants.length > 0` on the legacy branch throws, forcing customers through the real system once the founder sets one up for that product. Don't remove this dual path casually — it's the reason nothing broke mid-rollout, not leftover cruft.

**`VariantsModule`** (`src/variants/`): `POST /products/:productId/variants`, `PATCH /variants/:id`, `DELETE /variants/:id`, all `@Roles(ADMIN, MANAGER)`. Duplicate color+size is rejected at the **application layer**, not just the DB — Postgres treats `NULL != NULL`, so two color-less same-size variants wouldn't collide on the `@@unique([productId, color, size])` constraint alone. `DELETE` is blocked (400, not silently allowed) if any `OrderItem` already references the variant — "set stock to 0 instead" is the message; a variant that's genuinely never been ordered can be hard-deleted freely (no soft-delete needed there, unlike `Product`).

**5-image cap** added to both `Product.images` and `ProductVariant.images` via `@ArrayMaxSize(5)` on the create/update DTOs (matches the user's explicit ask).

`ProductsService.findBySlug`/`findOneForStaff` now `include: { variants }` (list endpoints don't, to keep those payloads light) — `GET /products/:slug` is what the storefront actually reads to decide real-vs-legacy rendering.

Verified live with curl: variant CRUD, duplicate rejection (color+size and SKU), 6-image rejection, an order against real stock (correct decrement), an order that exceeds stock (clear 400), delete blocked once ordered vs allowed when never ordered, and the dual-path transition itself (legacy order succeeds on a variant-less product, then gets rejected with the exact right message the moment a variant is added for that same product). `src/orders/` (`OrdersController`/`OrdersService`), all under `@UseGuards(JwtAuthGuard)`, scoped to `@CurrentUser()` (a 404, not 403, on someone else's order — same ownership pattern as Addresses):
- `POST /orders` — body is `{ addressId, items: [{productId, size, quantity}] }`. **Price is always server-computed** from the live `Product.priceInPaise`, never trusted from the client. Each cart line's `quantity` is expanded into that many individual `OrderItem` rows inside the transaction (per the standing "no `quantity` column" rule — every shirt is its own NFC-serialized unit).
- **GST is carved out of the tax-inclusive total, not added on top** — Cart/Product Detail already show prices as "Taxes Included" to the customer, so adding GST at order time would silently overcharge beyond what was shown. `gstAmountInPaise = round(total * 0.12 / 1.12)` (12% is the standard apparel-above-₹1000 GST slab; Day01's prices are all well above that). If the buyer's address state matches `SELLER_STATE` (case/whitespace-insensitive compare) → split into `cgstInPaise`/`sgstInPaise` (roughly half each, remainder to sgst to avoid rounding loss); otherwise → all `igstInPaise`. Verified live with a same-state (Karnataka) and cross-state (Delhi) address side by side — CGST+SGST vs pure IGST both came out correct.
- **`Invoice` row is created in the same transaction**, with a real sequential number (`DAY01/{financial-year-start}/{0001}`, Indian FY = April–March) and `hsnCode: '6109'` (cotton T-shirts). **PDF generation is explicitly not built** — `pdfUrl` stays null; that's build-order step 5's remaining scope, not created here. Numbering is **count-based within the FY prefix inside the transaction** — fine at this project's order volume, but flagged as a spot that'd need a dedicated counter table (not a running count) if concurrent checkouts ever became common enough to race on it.
- `Order.shippingAddress` is a full snapshot of the selected `Address` row's fields at order time (not just an id) — editing or deleting that saved address later never changes what a past order says it shipped to.
- `Order.status` is set to `CONFIRMED` immediately on creation — there's no payment-gateway webhook to wait on for COD, unlike the eventual Razorpay/Cashfree flow.
- `GET /orders` (own list) / `GET /orders/:id` (own detail, 404 if not owned) — both `include` items+product+invoice, used by `dayone-web`'s Account Home Overview tab and Order Confirmation page.

Verified live with curl: same-state order (CGST+SGST, both ≈half of the GST amount, no rounding mismatch), cross-state order (pure IGST), invoice numbers sequential across both (`DAY01/2026/0001`, `.../0002`), a quantity-2 line correctly producing 2 separate `OrderItem` rows, unauthenticated 401, an inactive/nonexistent product id 400, someone else's address id 404 (not silently allowed), empty `items` array 400, and cross-user order-list isolation. All test orders/invoices/addresses/users cleaned from `day01_db` after (invoice → orderItem → order → address → user, in that FK order).

## Auth + role system (build order step 2 — done, verified end-to-end)

Three roles on one `User` table (not a separate staff table — solo founder + at most one manager, matches §2's "avoid premature complexity"): `CUSTOMER` (default, self-signup), `MANAGER`, `ADMIN`. Decided with the user 2026-09-07: Manager gets full order access (same as Admin, including payment/GST detail — not read-only), Admin-only on analytics and on creating/managing staff accounts.

**What's built**, all under `src/auth/` and `src/users/`, plus shared pieces in `src/common/`:
- `POST /auth/signup` — bcrypt hash, **always forces `role: CUSTOMER` server-side**; the global `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })` in `main.ts` hard-rejects (400) any request body with an unexpected field at all — tested by sending `role: "ADMIN"` in a signup request and confirming it's rejected, not silently stripped.
- `POST /auth/login` — bcrypt compare, returns `{ accessToken, user }`. JWT payload is `{ sub: userId, role }`.
- `POST /auth/forgot-password` / `POST /auth/reset-password` — token is `crypto.randomBytes(32)`, only the **sha256 hash** is stored (`User.passwordResetToken`), 1-hour expiry (`passwordResetExpires`), single-use (cleared on successful reset). Always returns a generic success message regardless of whether the email exists, to avoid leaking registered emails. **No email provider wired up yet** — the raw reset token is `console.log`'d server-side as a placeholder (`// TODO` in `auth.service.ts`) so the flow is testable end-to-end; replace with real transactional email before launch.
- `POST /users/staff` (Admin-only, `@Roles(Role.ADMIN)`) — the only way to create a `MANAGER`/`ADMIN` account after bootstrap. `CreateStaffDto.role` is restricted to `MANAGER`/`ADMIN` via `@IsIn` (can't use this endpoint to create a customer).
- `src/common/guards/jwt-auth.guard.ts` + `roles.guard.ts` + `src/common/decorators/roles.decorator.ts` (`@Roles(...)`) + `current-user.decorator.ts` (`@CurrentUser()`) — the reusable pattern for gating any future route: `@UseGuards(JwtAuthGuard, RolesGuard) @Roles(Role.ADMIN, Role.MANAGER)`.
- **Bootstrapping the first Admin**: `prisma/seed.ts`, run via `pnpm run seed`. Reads `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD` from `.env`, no-ops if that email already exists. Already run once in dev — `admin@day01.store` exists in `day01_db` with the placeholder password from `.env` (**change it** before this ever matters for real). Not an API route on purpose — there's no safe way to expose "create an admin" over HTTP before any admin exists to gate it.

**Gotcha hit and fixed — `JwtModule.register()` vs `registerAsync()`:** `JwtModule.register({ secret: process.env.JWT_SECRET })` reads the env var at **module-decoration time**, which happens on `import` — before `main.ts`'s `process.loadEnvFile('.env')` runs (import statements are hoisted ahead of any top-level code in the importing file). This silently produced `secret: undefined` and every login/signup 500'd with `Error: secretOrPrivateKey must have a value`, even though `JwtStrategy` (which reads the same env var inside its constructor, evaluated later at DI-instantiation time) worked fine. Fixed by switching to `JwtModule.registerAsync({ useFactory: () => ({...}) })` in `src/auth/auth.module.ts`, which defers reading `process.env` until DI resolution — after env is loaded. If any other module ever needs an env var inside a static `.register()`-style call, use the async form for the same reason.
